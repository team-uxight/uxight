## 1. 한 줄 정의

> UXight 는 LLM 가상 사용자로 웹 사용성 테스트를 대신 돌리고, 행동 로그에서 UX 문제를 진단해 개선안을 제안하며,
> **승인된 개선안을 자동 적용해 재실험으로 효과를 검증**하는 UX 리서처용 플랫폼이다.

기업체 한 줄: *"UX 리서처 한 명이 사용자 50명 규모 테스트를 하루 만에 돌린다."*

## 2. 타겟 · 문제 · 차별점

| | |
| --- | --- |
| **1차 타겟** | UX 리서처 / 디자이너. **모든 설계 결정의 기준.** 개선안 상세에 행동 근거·Taxonomy·심각도까지 보여주고, 개선안은 "디자인 변경"으로 표현한다 |
| **2차 타겟** | 디자이너 없는 소규모 팀. 기대효과·확장에서만 언급 |
| **문제** | 사용성 테스트는 모집·진행·분석이 비싸다. UXAgent(2502.12561)는 테스트를 LLM 으로 시뮬레이션했지만 **문제 발견과 개선은 여전히 사람 몫**이다 |
| **vs UXAgent** | 시뮬레이션 → **진단 → 개선안 → 자동 적용 → 재실험** 까지 |
| **vs Hotjar / Maze / FullStory** | 실사용자 데이터 없이 **출시 전에**. 사후 분석이 아니라 **개선안까지** |

## 3. 범위

### In — 15주 안에 약속하는 것

| 영역 | 내용 |
| --- | --- |
| 대상 | **임의 URL 입력.** 동작 보장·데모 검증은 1~2개 사이트(가천대 포털 등) |
| Persona | 3종: Novice / Expert / Mobile-viewport (Playwright 디바이스 에뮬레이션) |
| 탐색 | Task 기반. UXAgent 방식의 브라우저 조작(click / type / scroll / back) |
| 진단 | **UX Friction Taxonomy 7종** — Navigation Confusion · Discoverability · Interaction Failure · Information Overload · Misleading Label · Task Failure · Excessive Steps. 각 진단에 행동 근거 + 심각도 |
| 개선안 | 3안 + 근거 + 예상 영향 / 수정 비용 |
| 적용 | **DOM 패치 4종만**: ① 라벨 변경 ② 요소 이동 ③ 요소 강조 ④ 도움말 삽입 |
| 승인 | 모바일 앱에서 알림 → 상세 → 승인/반려 (Human-in-the-loop) |
| 재실험 | 승인 즉시 같은 Persona 재투입. Before/After 지표: 성공률 · 행동 수 · 백트래킹 |
| 검증 | **축소 실사용자 실험**: 팀원 외 5~10명, 지표 3개(성공률 · 소요시간 · SUS). AI 예측 방향과 비교 |

DOM 패치를 4종으로 제한하는 이유: 이 4종은 사이트 구조와 무관하게 안정적으로 적용 가능하고,
카톡 outline 의 개선안 예시(메뉴명 변경 · 버튼 위치 · 도움말)가 전부 여기 들어간다.

### Out — 하지 않는 것

- 앱의 개선안 자동 적용·재실험 (컴파일된 앱 UI 는 외부에서 못 바꾼다)
- 코드 생성형 개선안
- IA 재편 같은 **구조 변경**의 자동 적용 (제안까지만)
- Persona 별 개인화 개선안 (카톡 outline 8번)
- 20명 규모 UT, NASA-TLX

### Phase 2 — 10/25 게이트

| 항목 | 조건 | 내용 |
| --- | --- | --- |
| **앱 드라이버** | S3 말(10/25) 진척 ≥ 50% | Appium 기반 AppDriver. **진단까지만.** 적용은 사람이 |

앱 탐색 자체는 확립된 기술이다 (AppAgent CHI 2025, Mobile-Agent-v3, AndroidWorld ICLR 2025).
게이트를 두는 이유는 기술이 아니라 **볼륨** — A(웹) 만으로 15주 풀 프로젝트이고 앱 드라이버는 +25~35%.
제안서·설계서에는 "웹 우선, 같은 구조로 앱 확장" 으로 쓴다. 제안서는 성적 미반영, 최종은 60% —
적게 약속하고 더 보여주는 쪽이 싸다.

## 4. 핵심 유저 플로우 (하나)

```
[웹] 프로젝트 생성 (URL · Task · Persona)
  → 실행
  → 진단 결과 (문제 · 근거 · 심각도)
  → 개선안 3안
[앱] 알림 → 개선안 상세 → 승인
  → 자동 DOM 패치 → 재실험
[웹] Before / After 대시보드
  → 실사용자 결과 입력 → AI 예측과 비교
```

## 5. 아키텍처 원칙 — Driver 추상화

```
Driver 인터페이스: observe() → 화면 트리 · act(action) · 행동 로그
  ├ WebDriver  (Playwright, DOM)          ← In
  └ AppDriver  (Appium, 접근성 트리)       ← Phase 2
```

Friction 진단은 **행동 기반**(왕복 · 반복 · 실패 · 경로 길이)이라 드라이버가 뭐든 재사용된다.
로그 스키마를 처음부터 드라이버 중립으로 잡는 것이 Phase 2 의 전제다.

## 7. 데모 시나리오 · 성공 기준

**데모** 가천대 포털, Task "장학금 신청 방법 찾기". 기준선 → 진단 → 라벨 변경 승인 → 재실험 → 지표 비교.

**최종 시연에서 확인할 것**
1. 임의 URL + Task 로 Persona 10명 실행이 **5분 내** 끝난다
2. 진단마다 Taxonomy 분류와 행동 근거가 붙어 있다
3. 앱에서 승인하면 웹 재실험이 **자동으로** 돈다
4. Before/After 지표 3개가 대시보드에 나온다
5. 실사용자 5~10명 결과와 AI 예측 방향 비교표가 있다
