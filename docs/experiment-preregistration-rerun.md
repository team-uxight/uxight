# 5명 연구 재실험 사전등록 (GACA-234)

이 파일을 처음 올린 커밋의 날짜가 기록 날짜다(2026-11-07). 실험은 이 파일을 병합한 뒤에 시작한다. 가설과 판단 규칙은 실험을 시작할 때의 규칙으로 한다. 실험을 시작한 뒤 규칙을 바꾸면 변경 기록에 적고, 바꾼 규칙의 값은 참고로만 쓴다.

사람 기준선 세션(GACA-197)까지 끝나면 seed · 정답 파일 · 사본 주소 대응표 · 후보 목록 · 결함 주입기 · 스크립트를 공개한다. 그때 누구나 아래 해시와 맞는지 확인할 수 있다.

## 왜 다시 재는가

- 11/07 결함 주입 실험([사전등록](experiment-preregistration.md))에서 5명 연구의 두 가설은 '판단 못 함'이었다.
- 판단값의 분모가 2개로, 문턱 6개보다 적었다. 분모는 모든 페이지 결함을 뺀 결함 가운데 Persona 가 한 명이라도 그 페이지를 연 결함이다.
- 결함 자리를 Task 와 상관없이 뽑아서, Persona 가 지나간 결함이 적었다.
- 이번에는 Persona 가 실제로 지나가는 페이지에만 결함을 심고 다시 잰다.
- 단일 · 다중 진단 비교(GACA-181)는 11/07 에 판단을 마쳐 다시 하지 않는다.

## 가설

11/07 과 같다.

- H1: 평균 재현율이 80% 를 넘는 가장 작은 인원(n80)이 5명 이하다. 80% 와 같으면 넘은 것이 아니다.
- H2: 5명 묶음 가운데 하위 10% 의 재현율이 60% 이상이다. 하위 10% 는 묶음의 재현율을 낮은 순으로 놓았을 때 묶음 수의 10% 자리 값이다.

- 구현 4유형은 진단이 잡도록 구현한 네 유형(길 찾기 혼란 · 조작 실패 · 과제 실패 · 과도한 단계)이다. 미구현 유형은 아직 구현하지 않은 유형이고, 미끼는 결함처럼 보이지만 결함이 아닌 것이다.
- Task 배분을 바꾼 까닭: 5명 묶음의 차이가 Task 배분이 아니라 Persona 에서만 나오게 하려는 것이다. 한 명이 Task 하나만 돌면, 5명 묶음에 어느 Task 의 Persona 가 들어가느냐에 따라 지나갈 수 있는 페이지가 달라진다.
- 다중만 돌리는 까닭: 5명 연구는 다중 진단의 근거를 Persona 별로 나눠 센다. 단일 진단은 쓰지 않고, 회차마다 Persona 25명이라 답이 잘릴 위험도 크다.
- 명단 규칙을 바꾼 까닭: 세 회차 가운데 일부만 진단을 받은 Persona 를 넣으면, 진단을 못 받은 Task 의 페이지가 빠진 채 한 사람으로 세어져 그 사람의 재현율이 낮게 나온다.
- 11/07 사본 s1~s4 와 Caddy 설정은 바꾸지 않는다. 사람 기준선은 s1~s4 를 그대로 쓴다.

## 사본

- 결함 사본 3개(A · B · C)를 만들었다. seed 는 사본마다 63비트 무작위 수다(Python `secrets.randbits(63)`).
- 결함 주입기에 후보 목록을 주면, 구현 4유형 결함을 목록의 페이지에 한 쪽에 하나씩 심을 수 있는 만큼 심는다. 하나도 못 심으면 멈춘다. 세 사본 모두 멈추지 않아, 처음 뽑은 seed 를 그대로 썼다.
- 정답을 열지 않고 센 구현 4유형 결함은 사본마다 4개, 합계 12개다. 세는 스크립트(`denominator-check.py`)는 개수만 출력한다.
- 결함 주입기의 출력은 파일로만 보내고 열지 않았다. 사본을 만든 사람은 seed · 정답 · 대응표를 보지 않고 해시만 확인했다.
- 원본과 결함 사본 3개를 실험 주소 x1~x4 에 무작위로 놓았다. 놓는 경우가 24가지뿐이라 대응표에 16바이트 무작위 값(salt)을 넣고 해시했다. 이 값이 없으면 해시로 대응표를 거꾸로 찾을 수 있다.
- 네 사본의 파일 · 폴더 시각을 모두 한 값으로 맞췄다. 원본 사본만 시각이 달라 어느 주소가 원본인지 드러나지 않게 하려는 것이다.

## 지표와 판단

찾았다의 기준과 곡선 계산은 [11/07 사전등록의 '지표' 절](experiment-preregistration.md#지표)과 같다. 다른 점만 적는다.

- **H1 · H2 는 조작 실패 결함만으로 판단한다.** 과제 실패 결함은 놓인 쪽에 따라 맞힘이 미리 정해지기 때문이다.
  - 과제 실패 진단은 성공 URL 에 한 번도 닿지 못한 Persona 에만 붙는다.
  - 답 페이지(`/kor/1163` · `/kor/3126`)에 놓인 과제 실패 결함은, 그 Task 의 Persona 가 들어서는 순간 성공이라 찾을 수 없다.
  - `/kor/1146` · `/kor/3219` 에 놓인 과제 실패 결함은 결함이 없어도 맞힘이 나온다. 원본 사본에서도 Task 1 · 3 의 실패한 실행이 이 두 페이지를 지나거나 여기서 끝난다.
  - 과제 실패 결함의 곡선과 구현 결함 전체의 곡선은 참고로 같이 낸다.
- 조작 실패 결함은 세 사본을 합쳐 6~9개다. 정답을 열지 않고 따져 낸 값이다. 사본마다 구현 결함이 4개 심겼다. 목록에 심을 수 있는 구현 항목은 조작 실패 3개 · 과제 실패 2개뿐이고, 항목마다 한 번만 뽑히기 때문이다.
- 판단은 세 사본을 합쳐서 한다. 분모는 합친 명단의 Persona 가 한 명이라도 그 페이지를 연 조작 실패 결함이다. 연 페이지는 step 의 `url`, 곧 모델이 본 화면이다.
- 분모가 6개 미만이거나 합친 명단이 20명 미만이면 H1 · H2 는 '판단 못 함'으로 적고 곡선만 보고한다.
- 원본 사본의 진단을 세 결함 사본의 정답(조작 실패 결함)으로 채점한 합친 곡선(우연 기준선)을 H1 · H2 옆에 적는다. 결함이 없어도 같은 페이지 · 같은 유형의 진단이 나오면 맞힌 것으로 나오기 때문이다. 우연 기준선에서도 H1 이나 H2 가 맞다고 나오면, 그 가설은 결함을 찾은 결과로 볼 수 없어 '판단 못 함'으로 적는다. 우연 기준선이 '판단 못 함'이면(원본 사본의 명단이 20명 미만이면) 본 판단도 '판단 못 함'이다.
- 한 사본에서 Persona 의 세 회차가 모두 진단을 받아야 그 사본의 명단에 든다. 명단에서 뺀 Persona 는 그 사본의 어떤 값(연 페이지 · 진단 근거 · 비용 · 오탐)에도 넣지 않고, 뺀 수를 결과에 적는다. 합친 곡선은 세 사본 모두의 명단에 든 Persona 만 쓴다.
- 미구현 · 미끼 결함이 조작 실패 결함과 같은 페이지에 놓이고 그 페이지에 조작 실패 진단이 붙으면, 조작 실패 결함을 맞힌 것으로 센다. 찾았다의 기준이 유형과 페이지만 보기 때문이다.
- 판단에 쓰는 값은 H1 · H2 와 우연 기준선이다. 오탐(원본 사본에서 Persona 실행 하나당 건수) · 노출률 · L(한 사람이 찾는 결함의 비율) · 결함 하나당 비용은 참고로 같이 낸다. 11/07 의 정밀도는 이번에 내지 않는다.
- L 은 문헌의 31% 와 바로 견주지 않는다. Persona 가 Task 셋을 모두 돌지만, Task 가 셋뿐이고 결함이 네 쪽에만 있다.

## 분석 순서

1. `run-g234.sh` 로 benchmark 를 돌린다. 설정에는 정답 파일과 원본 표시가 없다.
2. 같은 스크립트가 그 결과 폴더로 다중 진단을 한 번 돌린다.
3. 정답을 열기 전에 세 가지를 본다. 어느 주소가 원본인지 드러날 수 있어, 오탐 줄 · 진단 수는 보지 않는다.
   - 진단 없이 마감한 실행: `grep -c '진단 없이 마감' ~/g234/diag-a.log` 로 그 줄의 수만 본다.
   - 네 사본 모두의 명단: 사본마다 `discovery-curve.py --run <benchmark 폴더>=<진단 폴더>/multi --site <주소> --original --out <파일>` 을 돌리고, 결과에서 `grep '명단에서 뺀 Persona'` 로 그 줄만 본다. 네 결과에서 뺀 Persona 를 모아 25명에서 뺀 수가 네 사본 모두의 명단이다.
   - 입력 검사: 내용이 서로 다른 가짜 정답 파일 셋으로 합친 곡선을 한 번 돌려, 입력 검사를 통과하는지 본다.
4. 진단이 모두 끝난 뒤 채점 담당이 정답 파일과 대응표를 연다. 해시가 위 표와 같은지 먼저 확인한다.
5. 저장된 진단 결과만 채점한다. 정답을 넣고 진단을 다시 돌리지 않는다. LLM 답이 달라져 사전등록한 실행의 결과가 아니게 되기 때문이다.

채점 명령은 아래와 같다. `<A>` · `<B>` · `<C>` · `<원본>` 은 대응표의 실험 주소이고, `<benchmark 폴더>` · `<진단 폴더>` 는 채점에 쓰는 마지막 폴더다.

```
# 판단 (조작 실패 결함, 세 사본 합침)
python3 scripts/discovery-curve.py --run <benchmark 폴더>=<진단 폴더>/multi \
  --defect <A>=experiment/answers/g234-A.json --defect <B>=experiment/answers/g234-B.json \
  --defect <C>=experiment/answers/g234-C.json --kind INT --seed 20261107 --out curve-int.md
# 우연 기준선 (판단에 씀)
python3 scripts/discovery-curve.py --run <benchmark 폴더>=<진단 폴더>/multi --chance \
  --defect <원본>=experiment/answers/g234-A.json --defect <원본>=experiment/answers/g234-B.json \
  --defect <원본>=experiment/answers/g234-C.json --kind INT --seed 20261107 --out curve-int-chance.md
# 참고: 과제 실패 결함 (판단 명령에서 --kind TASK, --out curve-task.md)
# 참고: 구현 결함 전체 (판단 명령에서 --kind 를 빼고, --out curve-all.md)
# 참고: 원본 사본 오탐
python3 scripts/discovery-curve.py --run <benchmark 폴더>=<진단 폴더>/multi --site <원본> --original --out curve-original.md
```

## 세지 않는 것과 다시 돌리는 때

- 판정 안 함(실행 오류 · 취소 · 도달 기록 없음)과 진단 없이 마감한 실행의 수를 결과에 적는다.
- 다시 돌리는 차례는 아래와 같다. 모두 정답을 열기 전에 하고, benchmark · 진단 각각 한 번까지만 다시 돌린다.
  1. 진단 없이 마감한 Persona 실행이 있으면, 까닭과 상관없이 진단만 새 폴더로 다시 돌리고 그 결과를 쓴다.
  2. 그다음 네 사본 모두의 명단에 든 Persona 가 20명 미만이거나, LLM 호출 실패나 사본 서버 장애로 끝난 Persona 실행이 10% 를 넘거나, benchmark 가 종료 코드 0 이 아니게 끝났으면, benchmark 를 처음부터 다시 돌리고 앞선 폴더는 쓰지 않는다. 새 benchmark 의 진단에도 1번을 한 번 쓸 수 있다.
  3. 그래도 기준에 못 미치면 더 돌리지 않고 마지막 폴더로 채점한다. '판단 못 함' 규칙은 그대로 따른다.
- 다시 돌린 폴더는 앞 폴더와 끝 이름을 다르게 짓는다(benchmark 는 `g234-b`, 진단만 다시 돌리면 `g234-a-diag2`). 다시 돌린 일은 변경 기록에 적는다.
- 실험 동안 develop 병합을 멈춘다. 실행 스크립트는 시작할 때와 진단 직전에, VM 에 배포된 커밋과 `~/uxight` 의 커밋이 정한 커밋과 같은지, 그 커밋에 이 파일이 있는지 보고, 아니면 멈춘다.

## 한계

결과에 같이 적는다.

1. **판단은 조작 실패 한 유형으로 한다.** 심은 구현 결함은 조작 실패 · 과제 실패 두 유형뿐이다. 길 찾기 혼란은 모든 페이지 결함뿐이라 뺐고, 과도한 단계는 목록에 놓을 자리가 없다(탭을 옮겨야 겪는 결함인데, 다른 탭 페이지가 목록에 없다). 과제 실패는 판단에서 빼고 참고로만 둔다(지표와 판단). 그래서 '5명이면 충분한가'라는 물음에 이 실험은 구현 4유형(Friction) 가운데 조작 실패 한 유형만 답한다.
2. **결함이 같은 4쪽에만 놓인다.** 결함을 받을 수 있는 쪽은 `/kor/1146` · `/kor/1163` · `/kor/3126` · `/kor/3219` 넷이다. 결함 주입기는 홈에 심지 않고, `/kor/12490` 에는 놓을 수 있는 항목이 없다. 항목마다 놓일 수 있는 쪽은 정해져 있고, seed 는 어느 항목이 어느 쪽 어느 자리에 놓이고 어느 항목이 빠지는지를 정한다. 결과를 사이트 전체로 넓혀 말하지 않는다.
3. **분모는 상한이다.** 구현 결함 12개와 조작 실패 결함 6~9개는 목록의 페이지에 심은 수다. 실제 분모는 명단의 Persona 가 그 페이지를 연 결함의 수다. 25명이 Task 셋을 모두 돌아 상한과 거의 같을 것으로 본다.
4. **우연 기준선이 빼지 못하는 몫이 있다.** 결함 사본에 같이 심은 미구현 · 미끼 결함이 조작 실패 진단을 낳아도, 그 진단이 조작 실패 결함과 같은 페이지면 맞힌 것으로 센다. 우연 기준선은 원본 사본으로 재므로 이 몫을 빼지 못한다.

이 밖에 같이 적는 것:

- 커밋 · 모델 · 정답 파일 해시
- 판정 안 함 · 진단 없이 마감한 실행의 수
- step · 시간 상한에 걸려 끝난 Persona 실행의 비율과 시간 초과 step 수
