**회사 프록시 탐침 결과(09/14, `scripts/probe-llm-api.py`):** OpenAI-호환. `beta.chat.completions.parse(response_format=PydanticModel)` · `response_format=json_object` · function tool calling **셋 다 동작**했다(gemini-3.8-flash). rate-limit 헤더는 내려오지 않는다.
- 구조화 출력(Persona 의 다음 행동 · 진단 · 개선안 JSON)은 **`response_format` 으로 스키마를 강제하고 pydantic 으로 검증, 실패 시 재시도**. 프롬프트-only 파싱보다 실패율이 낮다.
- **tool calling 은 되지만 쓰지 않는다** — LLM 에게 실행 능력을 주지 않는다는 격리 원칙(D18). 액션은 JSON 응답이고 실행은 Runner 가 한다.
- 이 방식은 OpenRouter · OpenAI 로 갈아타도 그대로라 **제공자 교체가 설정값 하나**로 유지된다.
- "multi-agent orchestration" 의 실체는 **Persona N개(10~50)를 동시에 돌리는 것** — `asyncio.gather` + 세마포어(동시 상한) + 브라우저 1개에 context N개. 에이전트끼리 협상하는 구조가 아니므로 프레임워크 없이 표준 라이브러리로 충분하다.

## 4. BE 언어 — Java + Spring 확정 (조건부, 09/12)

### 결정

**Java + Spring + MySQL.** 원칙 ①("팀원이 써본 기술 우선")이 이겼다.
한재완님의 Python 경험은 "프로젝트에서 몇 번 써봤지만 AI 에 물어가며 쓴 수준" 이고, Java/Spring 이 가장 편하다.

**조건부다.** 되돌릴 조건과 시점을 함께 정했다:

| | |
| --- | --- |
| 조사 | 한재완 — **Java ↔ Python 통합 비용** |
| 전환 조건 | 통합 비용이 크다고 판단되면 **FastAPI 로 전환** |
| 확인 시점 | **10월 초 (10/5~10/11 주)** — 최소한의 요구분석·설계 후, AI 가 Persona Agent(2번)까지 만든 상태에서 **통합 프로토타입을 먼저 붙여본다** |

늦게 갈아타는 비용을 줄이려고 통합을 앞당긴 것이다. S1 설계 때 **경계(무엇을 Spring 에 두고 무엇을 Python 에 둘지)를 먼저 긋는다.**

### 조건부 설계의 문제 3가지 (PM 검토, 09/13) → 09/14 게이트 재설계로 해소

**결정 자체(Java/Spring)는 방어 가능하다.** 담당자에게 낯선 언어를 강제하면 BE 가 느려지거나 결국 PM 이 떠안는데,
PM 은 이미 배정 155h / 가용 120h 로 초과 상태다(`assessment-2026-09-12.md`). 그 위험을 키우는 선택이 더 나쁘다.
문제는 **되돌릴 장치가 실제로 작동하지 않게 설계되어 있다는 것**이다.

| # | 문제 | 왜 문제인가 |
| --- | --- | --- |
| 1 | **트리거가 주관적이다** — "통합이 많이 어려우면" | 누가 무엇을 보고 판단하는지가 없다. 이런 게이트는 거의 항상 "조금만 더 하면 될 것 같은데" 로 끝나 전환되지 않는다 |
| 2 | **시점이 늦다** — 10/11 | 10/14 중간발표(개발 30%), 10/23 진도표(50%)가 바로 뒤다. 10/11 에 문제가 보여도 "지금 갈아타면 중간발표를 망친다" 가 되어 못 바꾼다. **pivot 옵션이 사실상 없는 것과 같다** |
| 3 | **진짜 리스크를 겨냥하지 않는다** | Spring↔Python 을 HTTP 로 "붙이는" 건 어렵지 않다. 어려운 건 ①**10분 넘게 도는 작업의 상태 관리**(비동기 잡·폴링/콜백·부분 실패) ②**스키마 이중 정의**(Java DTO + pydantic, 설계 초기엔 매주 바뀐다) ③서비스 2개의 배포·로컬 실행 |

### 제안 — pivot 이 필요 없도록 경계를 다시 긋는다

| | |
| --- | --- |
| **Spring** | CRUD · 인증 · 조회 전용 |
| **Python** | 실행 전부 — 오케스트레이션 · 로그 · 진단 · DOM 패치 · 재실험 |
| **연결** | Spring → Python 은 **"실행 시작" 호출 하나**(fire-and-forget). 이후 상태는 **Python 이 MySQL 에 쓰고 Spring 이 읽는다** |

이러면 HTTP 계약이 **엔드포인트 1개**로 줄고, **§4 문제 3의 ①상태 동기화가 통째로 사라진다**(단일 진실 = DB).
`asyncio + 세마포어`(§3) 설계도 그대로 살아남는다.

- **단점:** 공유 DB 는 마이크로서비스 관점에선 안티패턴이다. 서비스 2개 · 15주 · 내부 시스템이라 감수할 만하지만,
  **테이블 소유권을 명시**해야 한다 — Python 이 쓰는 테이블은 Spring 에서 읽기 전용, 마이그레이션 주체는 하나.
- **대안:** Python 이 Spring 내부 API 로 로그를 쓴다. 소유권은 깔끔하나 run 중 호출이 잦고, Spring 이 떠 있어야 Python 이 돈다.

| | 현재 | 제안 |

| 실패 시 | Python 전환 | 같음. 단 **이 시점이면 버릴 코드가 며칠치뿐** |

**"설계가 나온 뒤에 통합을 본다" 는 순서가 곧 pivot 을 불가능하게 만드는 원인이다.**


### 결정 당시 기록해 둔 반대 논거 (PM)

BE 책임 7개 중 4개 — Persona 병렬 실행 오케스트레이션 · 행동 로그 수집/지표 · 승인→DOM 패치→재실험 트리거 —
가 Python Agent 코드에 붙어 있다. 그래서 PM 권장은 FastAPI 단일 서비스였다.

| | **A. Spring API + Python AI 서비스 (채택)** | **B. FastAPI 단일 서비스** |
| --- | --- | --- |
| 한재완 초반 속도 | 빠름 (익숙) | FastAPI 램프 약 1주 |
| 서비스 · 배포 | 2 · 2 | 1 · 1 |
| Agent 호출 | HTTP 계약 (JSON 스키마 유지·버전) | 함수 호출 |
| 오케스트레이션 | Spring → Python 서비스에 "실행해" 요청 → 상태 폴링/콜백 | 같은 프로세스, asyncio |
| 한재완의 하루 | BE 는 Java, AI 는 Python — 두 언어 | 한 언어 |

**A 의 실제 비용은 계약·배포 순서·상태 동기화에서 나온다.** 10월 초 프로토타입에서 볼 것이 정확히 이것이다.

## 8. 스케일 적정성 검토 (2026-09-13, PM)

### 8.1 이 시스템의 실제 규모

| 축 | 값 | 근거 |
| --- | --- | --- |
| 동시 사용자 | **1~2명** (리서처). 동시 쓰기 주체는 사실상 1 | D4 |
| 데이터 총량 | 15주 **수백 MB**, 대부분 행동 로그 | T2 가정 |
| 요청률 | 초당 요청이라는 개념이 없다. **한 run 이 10분 이상** | |
| 병목 | **LLM 호출 지연 + 브라우저 동시 실행 메모리** (DB·프레임워크가 아니다) | |
| 배포 | 서버 1대 | O12 |

**순수하게 규모만 보면 정답은 "SQLite + 단일 Python 프로세스"다.** 지금 구성은 원칙 ①(팀이 써본 기술)로 그것을 덮은 것이고,
그 대가가 얼마인지 아래에 적는다. 원칙 ①은 옳다 — 문제는 대가를 모르고 치르는 것이다.

### 8.2 항목별 판정

| 영역 | 판정 | 근거 | 조치 |
| --- | --- | --- | --- |

### 8.3 아직 아무도 보지 않은 병목 — 실험 1회 소요 시간

비용(`llm-cost.md`)은 계산했지만 **시간**은 계산한 적이 없다.

- 제안서 예시는 **Persona 50명**, T5 의 동시 상한은 10, `llm-cost.md` 는 "초반 동시 2~3".
- Persona 1명 ≈ step 최대 20 × (LLM 지연 2~5초 + 페이지 로드) ≈ **5~10분**.
- **50명 ÷ 동시 4 × 7분 ≈ 90분.** Before/After 비교면 **3시간.** 조건당 N회 반복이면 그 배수.

즉 **비용보다 시간이 먼저 막힌다.** 발표 시연에서 실시간으로 돌릴 수 없고, 반복 실험도 하루 몇 회로 제한된다.

메모리도 같은 축이다. **브라우저는 1개만 띄우고 context 를 N개** 쓴다(browser 를 N개 띄우면 안 된다).
context 당 수백 MB 이므로 동시 실행 상한은 서버 RAM 으로 결정된다.

**조치**
1. S1 에 **"동시 실행 상한 실측"** 을 넣는다 — Persona 1명 소요 시간 · context 당 메모리 · 서버 RAM 기준 상한.
2. **데모·실험 기본값은 Persona 5~10.** 제안서의 50 은 "규모 예시" 로 두고 실제 기본값과 분리한다.
3. 측정값이 나오면 `llm-cost.md` 에 **시간 축**을 추가한다 (현재는 비용 축만 있다).

### 8.4 종합

**낭비는 두 개 반이다.** 서비스 2개·언어 2개(정당화되지만 비용 있음) · LangChain(정당화 약함) · MySQL(작음).
되돌릴 가치 순서는 ~~LangChain(제거됨)~~ **통합 구조(§4) > MySQL(건드리지 않음)**.

그리고 **스케일 관점의 진짜 리스크는 프레임워크가 아니라 실험 소요 시간(§8.3)** 이다. 지금 아무도 보고 있지 않다.

## 9. 오케스트레이션 설계 평가 — Watcher · Master/Slave (2026-09-14, PM 질문)

PM 구상: ① 실제 UT 의 진행자처럼 **Watcher 가 하위 Persona Agent 50개를 오케스트레이션** ② Improvement → Rerun & Evaluator 루프에서
**Master/Slave 로 에이전트를 조직해 토큰 최적화** ③ 그러려면 에이전트끼리 통신(LangChain)이 필요하지 않나.

### 9.1 먼저 — 실제 UT 진행자는 무엇을 하는가

| 진행자의 일 | 우리 시스템에서의 대응 | LLM 필요? |
| --- | --- | --- |
| 세션을 굴린다 (시작 · 막히면 정리 · 시간 초과 종료) | **스케줄러** — step 상한 · 반복 감지 · 타임아웃 · 재시도 | 아니오 |
| "지금 무슨 생각이세요?" (think-aloud 유도) | Persona Agent 가 매 step 에 남기는 **reasoning 필드** (UXAgent Memory Stream) | 이미 있음 |
| 관찰을 기록한다 | **행동 로그** → 사후 Friction Detector | 아니오 |
| **절대 유도하지 않는다** — 힌트를 주면 실험이 망가진다 | Watcher 가 하위 에이전트에게 **내용을 말하면 안 된다** | — |

즉 진행자를 흉내내면 결론은 **"Watcher 는 제어면(control-plane)이지 대화 상대가 아니다"** 이다.
막힌 에이전트에게 Watcher 가 힌트를 주는 순간 성공률이 부풀고, 진단 결과가 실사용자와 갈라진다 (연구 가치 D10 훼손).

### 9.2 구상별 판정

| 구상 | 기술적으로 | 기간 내에 | 판정 |
| --- | --- | --- | --- |
| **A. Watcher = 규칙 기반 감독자** — 50개 실행 · 동시 상한 · 멈춤/루프 감지 · 재시도 · 진행률 이벤트 | `asyncio.gather` + 세마포어 + 큐. 100~200줄 | **S2~S3, 2~3일.** 이미 "오케스트레이터" 로 계획된 것 | **한다** |
| **B. Watcher = LLM 감독자** — 50개 trace 를 실시간으로 읽고 개입 (힌트 · 조기 종료 판단) | 가능. 단 50개 trace 를 주기적으로 읽는 것 자체가 **토큰을 곱한다** | S4, 1주+ | **하지 않는다.** 개입은 실험을 오염시키고(9.1), 관찰만 하는 LLM 은 사후 Detector 와 중복 |
| **C. Master/Slave 개선 루프** — Master 가 "누구를 · 어떤 패치로 · 몇 번" 재실행할지 정하고 Slave 가 실행 | 가능. 실체는 **정책 함수 3개**: 재실행 대상 선택(해당 Friction 에 걸린 Persona 만) · 조기 종료(지표 수렴) · Slave 는 저가 모델 | S4~S5, 1주. **D13 게이트(5·6 선택) 통과가 전제** | **정책으로 구현, 에이전트로 만들지 않는다** |
| **D. 에이전트 간 통신 프로토콜** (LangChain/LangGraph supervisor) | 가능하나 **회사 API 가 tool calling 을 못 해** LangGraph supervisor 의 handoff 경로가 막힘. 우회하면 프레임워크와 싸우는 코드가 됨 | 램프 1주 + 우회 비용 | **불필요.** 오가는 메시지가 `start(persona, task, patch_ver)` · `step_event` · `done(result, log)` · `error` 뿐 — **큐/DB 행이지 대화가 아니다** |

### 9.3 토큰 최적화는 어디서 나오나 (C 의 실체)

루프 1회 = Persona N 재실행이라 토큰은 **N × step × 루프 횟수**. Master 에이전트가 아니라 **세 가지 규칙**이 줄인다:

1. **부분 재실행** — 진단에서 해당 Friction 에 걸린 Persona 만 재투입 (50 → 10~20)
2. **조기 종료** — 성공률 · 행동 수가 이전 루프 대비 수렴하면 중단. 루프 상한은 리서처 옵션(D13)
3. **역할별 모델** (T12) — Slave(탐색)는 저가, Master 판단(진단 · 개선안)만 상위. 이건 이미 결정됨

이 셋은 오케스트레이터 안의 함수다. "Master 에이전트가 판단한다" 로 만들면 그 판단 자체가 토큰을 쓴다.

### 9.4 결론

- **구조는 PM 구상대로 간다** — 감독자 하나가 하위 실행을 조직하고, 개선 루프는 Master/Slave 로 돈다.
- **구현은 에이전트 대화가 아니라 스케줄러 + 정책 함수**다. 그래서 LangChain 은 여전히 필요 없다 (T15 유지).
- **기간:** A 는 S2~S3 에 확실. C 는 S4~S5, D13 게이트를 넘겨야 착수. B 는 하지 않는다.
- **실측이 먼저** — 50 동시 실행은 서버 RAM · rate limit 에 막힐 가능성이 크다 (GACA-70). 현실은 동시 5~10, 50은 큐잉.
- 나중에 그래프 시각화 · 체크포인트가 정말 필요해지면 그때 LangGraph 를 **S3 이후** 재검토. 지금 넣으면 tool calling 우회 비용만 진다.

## 10. "chat 만 되는 LLM API 로 웹 탐색 Agent 가 되는가" (2026-09-14, PM 질문)

**된다. 오히려 그게 원형이다.** Tool calling 은 "모델이 액션을 JSON 으로 내고, 바깥 코드가 실행한다" 를 제공자가 검증해 주는 편의 기능일 뿐,
에이전트 루프 자체는 항상 **우리 코드**에 있다. UXAgent · WebArena 기준선 · 초기 ReAct 계열이 전부 chat completion 하나로 돌았다.

```
loop (step ≤ 20):
  obs   = driver.observe()                 # Playwright → 정리된 DOM: 보이는 요소를 [n] 번호 목록으로
  prompt= system(persona, task, 행동 스키마) + history(최근 k step 요약) + obs
  text  = llm.chat(prompt)                 # chat completion 한 번
  act   = parse_json(text) → pydantic 검증 # 실패 시 "JSON 만 다시" 1~2회 재시도
  guard(act)                               # 허용 목록 · 도메인 · 파괴적 행동 (agent-safety §2)
  driver.act(act)                          # click [n] / type [n] "…" / scroll / back / done
  log(obs, reasoning, act, result)         # Detector 입력
```

### 되게 만드는 조건 4개

| 조건 | 왜 | 우리 대응 |
| --- | --- | --- |
| **요소는 번호로, 셀렉터는 안 준다** | 모델이 CSS 셀렉터를 지어낸다. `[12] button "해지하기"` 처럼 번호 목록을 주고 번호만 받으면 환각이 구조적으로 막힌다 | UXAgent 부록 A 의 단순화 HTML + 번호 매기기 |
| **관측을 잘라서 준다** | 원본 DOM 은 컨텍스트를 터뜨린다 | DOM pruning (T5) — 보이는 · 상호작용 가능한 요소만 |
| **JSON 강제 + 재시도** | 스키마 검증은 우리가 | `response_format` 으로 스키마 강제(탐침 확인) + pydantic + 재시도. 프롬프트-only 보다 실패율 낮음 (T16) |
| **히스토리 요약** | 20 step 의 관측을 다 넣으면 컨텍스트 초과 | 최근 3 step 원문 + 그 이전은 한 줄 요약 (UXAgent Memory Stream 의 축소판) |

### 못 하는 것 · 안 해도 되는 것

- **스크린샷 기반 판단** — vision 이 없는 chat 모델이면 불가. **v1 은 텍스트 DOM 만**으로 간다. 사람과의 클릭 패턴 차이("사람은 화면, AI 는 코드")는 여기서 나오고, 검증 실험(D10)에서 정직하게 보고할 항목
- **제공자 측 병렬 tool call · 스트리밍** — 필요 없다. 병렬은 Persona 단위로 우리가 돌린다 (§9)
- **모델 급에 따라 JSON 준수율이 갈린다** — flash 급에서 파싱 실패가 5% 를 넘으면 그 모델은 Agent step 에 못 쓴다. **T4 의 S3 A/B 항목에 "JSON 준수율" 을 넣는다**

### 확인할 것 (S1, PM)

탐침으로 ③JSON 모드는 확인됐다(§6). 남은 것은 ①캡스톤 키의 모델 목록 ②rate limit — 둘 다 제공자 확인.

### 탐색(Persona step)에 저가 모델을 써도 되는가 — "사람을 흉내내려면 추론 모델이어야 하지 않나" (09/14)

**실험으로 정할 문제이고, "강할수록 사람 같다" 는 가정은 근거가 약하다.** 정리:

| 관점 | 내용 |
| --- | --- |
| 사람 흉내의 실체 | 실제 사용자는 **제한된 합리성**으로 움직인다 — 훑어보고, 그럴듯한 걸 먼저 누르고, 헤맨다. 프론티어 추론 모델은 DOM 전체를 읽고 숨은 메뉴를 찾아내 **사람이 실패하는 곳에서 성공**한다 → Friction 을 **과소 검출**. UXAgent 리서처 평도 "너무 상세하다, 진짜 사람은 이렇게 생각 안 한다" 였다 |
| 너무 약하면 | JSON 오류 · 페르소나 무시 · 무의미한 루프 — **Friction 처럼 보이는 노이즈(오탐)** 를 만든다. Detector 의 적 |
| 사람다움의 진짜 레버 | 모델 급보다 **관측(무엇을 보게 하나)** 과 **페르소나 조건화** — 뷰포트 안만 보여주기 · 숨은 요소 제거 · 스크롤해야 보이는 건 스크롤 전엔 안 보이기 · 숙련도에 따른 step/시간 예산. Novice 가 Expert 와 같은 DOM 을 통째로 보면 모델이 뭐든 Novice 가 아니다 |
| 추론 모델의 실무 비용 | ①숨은 추론 토큰으로 **비용 5~20× · 지연 3~5×** — §8.3 의 시간 병목이 악화 ②많은 API 가 **추론 내용을 돌려주지 않는다** → 진단의 입력인 think-aloud(reasoning 필드)가 **빈다.** 우리는 보이는 추론이 필요하다 |
| 추론을 싸게 얻는 길 | UXAgent 의 Slow loop(Wonder/Reflect)를 **저가 모델로 명시적으로** 돌리면 추론이 로그에 남는다. 이게 진단에 쓰인다 |

**결정 방식 (T4 보강):** S3 1주차 A/B 에 후보 3급 — 저가(DeepSeek/Qwen 급) · 중간(flash/mini 급) · 추론 모델 — 을 놓고, 지표는 성공률이 아니라 **①JSON 준수율 ②결함 심은 테스트 사이트에서 "사람이 막히는 곳에서 막히는가"(재현율·오탐률) ③소규모 실사용자(D10)와의 경로 일치 ④비용·시간**. 성공률이 가장 높은 모델이 아니라 **사람과 가장 비슷하게 실패하는 모델**을 고른다.

**가설 하나 (실험 항목으로만):** 숙련도를 모델 급이 아니라 **관측·예산으로** 표현한다 — Novice = 뷰포트 제한 + 짧은 히스토리 + 저가 모델, Expert = 넓은 관측 + 긴 히스토리. 맞으면 탐색 비용은 낮게 유지하면서 페르소나 차이가 로그에 드러난다.

### Vision 으로 탐색시키면 어떤가 — "사람은 화면을 보고, 모델은 DOM 을 본다" (09/14)

**된다. 지연도 문제가 아니다. 관측 모드의 기본 후보로 올린다.**

**탐침 (`scripts/probe-llm-vision.py`, 회사 프록시 gemini-3.8-flash, 1280×720 SoM 스크린샷):**

| | Vision (SoM 스크린샷) | Text (요소 목록) |
| --- | --- | --- |
| step 지연 | **2.6 ~ 3.7s** (3회) | 2.1 ~ 4.1s |
| 프롬프트 토큰 | **~1,140** (이미지 포함) | 35 (요소 3개) — 실제 정리된 DOM 은 2~6K |
| 정답률 | 3/3 — "와우 멤버십 관리" 선택 | 정답 |

→ **스크린샷 1장 ≈ 1.1K 토큰으로 정리된 DOM 보다 싸고, 지연은 같은 급.** "vision = 느리고 비싸다" 는 이 프록시에선 사실이 아니다.

**방식 — Set-of-Marks (SoM) 하이브리드**, WebVoyager · browser-use 계열의 표준:
1. Playwright 가 상호작용 가능한 요소에 **번호 박스를 오버레이**한 스크린샷을 찍는다 (JS 주입, 100~300ms)
2. 모델에게 **스크린샷 + 짧은 요소 목록**(`[2] button "와우 멤버십 관리"`)을 주고 **번호**를 받는다 — 좌표 클릭이 아니라서 환각이 막힌다
3. 뷰포트 안에 보이는 것만 찍힌다 → **"스크롤 전엔 안 보인다" 가 공짜로 구현된다** (앞 절의 관측 레버)

**왜 사람다움에 유리한가:** 시각 계층 · 대비 · 크기 · 아이콘의 오해 · 접힌 메뉴 — DOM 에는 있지만 **사람 눈에는 안 보이는 것**을 모델도 못 보게 된다. "사람은 화면, AI 는 코드" 라는 갭(D10 리스크)을 **관측 단계에서** 줄이는 유일한 방법이다. 진단 쪽에도 스크린샷이 근거로 남아 리서처 화면의 "근거 보기" 가 강해진다.

**비용 · 리스크:**
- 구현 +10~15h (SoM 오버레이 · 스크린샷 파이프라인 · 저장). Persona Agent 와 같은 사람이 같은 스프린트에
- 저장: 50 Persona × 20 step × ~100KB ≈ 100MB/실험 → 보존 기간 정책 (S3)
- **개인정보:** 스크린샷에 입력값이 찍힌다 → agent-safety §1.2 마스킹을 이미지에도 (입력 필드 블러)
- 모델 제약: vision 지원 모델만 후보. 회사 프록시의 flash 는 된다 — 캡스톤 키 모델 목록에서 vision 가능 모델을 표시

**결정 (T18):** 관측 모드 기본 후보 = **SoM 하이브리드**. S3 A/B(T4)에 **관측 축(DOM-only vs SoM)** 을 추가해 사람 유사도 지표로 비교. Persona Agent 1차 구현은 SoM 으로 시작하되 DOM-only 로 떨어질 수 있게 관측을 인터페이스로 분리 (`observe()` 가 둘 다 낼 수 있게 — Driver 추상화 D9 안에).
